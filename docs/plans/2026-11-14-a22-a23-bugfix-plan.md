## A22 – white segment bar invisible on bright footage

**Evidence:** `docs/design/screenshots/app/2026-11-13/api35-en-07-segment-bar.png` (API 35, bright synthetic scene,
"Paused · 1 segment · 0:11"): no bar is visible at the top edge, although one segment is recorded.

**Root cause:** `SegmentProgressView.kt:20-21` paints the track in 33 % white (`0x55FFFFFF`) and finished segments in
pure white (`Color.WHITE`), drawn without any edge (`:60-61`, `:68-74`). On a white or very bright frame both have
zero contrast to the background. Only the live segment (green/orange/red, `:22-24`) and the armed segment (amber,
`:25`) have a colour of their own.

**Fix (contrast outline, no new style):**

- `app/src/main/java/de/codinix/videoeditor/SegmentProgressView.kt`
  - after `:25`: one `outlinePaint` – `Paint.ANTI_ALIAS_FLAG`, `style = Paint.Style.STROKE`,
    `strokeWidth = 1f * resources.displayMetrics.density`, `color = 0x8C000000.toInt()` (55 % black).
  - `onDraw` (`:56-95`): add a **last** pass after the review overlay (`:80-94`): stroke the track rect and each
    finished segment rect with the same geometry as `:60` and `:71` (rect inset by `strokeWidth / 2`, radius `r`).
    Drawing it last keeps the edge visible over the red playback fill in review; drawing it inside the `:68-74` loop
    would let the red overlay paint over the inner half of the stroke.
  - Track, segment, live, warning, armed and red colours, the 6 dp height (`activity_main.xml:29`), the gaps and the
    corner radius stay unchanged. The live segment needs no outline (it is saturated colour), but stroking it too is
    acceptable if it keeps the code simpler.
- No layout, string or theme change.

**Concept boundary:** the fix is in scope only as long as it is a thin dark edge around the existing shapes. A
shadow, a background pill, a scrim, a thicker bar or new colours are visible design and go to concept item 1 (with
A20). If the reviewer or Design-Abnahme counts the edge itself as design, PR-3 ships A23 alone and A22 moves to that
concept.

**Rejected alternatives:**

- `Paint.setShadowLayer`: hardware-accelerated shadow layers on shapes need API 28; with `minSdk 26` the view would
  need `LAYER_TYPE_SOFTWARE` for an element that redraws every frame while recording.
- Darker segment fill (e.g. grey): changes the bar's look on dark footage, which works today.

**Design rules applied (skills apple-design, ui-cheatsheet):** "Simplicity – clear hierarchy through contrast" and
"`prefers-contrast`: defined, contrasting border" (apple-design) – the edge gives a defined border instead of
relying on the background; "restraint / simplicity" – no new surface, colour or size. ui-cheatsheet has no rule
specific to this element.

**Tests:** no JVM test (drawing code only, no Robolectric in the project). `./gradlew assembleDebug lintDebug` green.

## A23 – review status shows position greater than total ("0:13 / 0:12")

**Evidence:** `docs/design/screenshots/app/2026-11-13/run1-api35-en-09-review-cut.png`.

**Root cause (two time bases):**

1. A segment's `durationMs` is the CameraX recording statistic `recordedDurationNanos / 1_000_000`
   (`MainActivity.kt:621`, stored at `:625` and in drafts). The player, however, plays the finished MP4 file, whose
   media timeline is usually a little longer (audio/video track ends do not match the recorded-duration counter).
2. `updateReviewPosition` (`MainActivity.kt:2722-2737`) mixes both: `pos = before + p.currentPosition` (`:2727`,
   `before` = sum of earlier `durationMs`, `currentPosition` = file timeline) against
   `total = segments.sumOf { it.durationMs }` (`:2728`). At the end of the last segment `pos` exceeds `total` by the
   file overrun (a few hundred ms).
3. `fmt()` (`:3270-3273`) truncates to whole seconds, so e.g. pos 13 100 ms / total 12 400 ms reads "0:13 / 0:12".
   The scrub bar's own labels (`ScrubBarView.kt:96`, `:127-129`, `fmt` at `:178-181` with tenths) show the same
   overrun ("0:13.1" vs "0:12.4"). The red review bar is already safe: `SegmentProgressView.kt:81` clamps its x.

**Fix (display clamp in a pure function):**

- New `app/src/main/java/de/codinix/videoeditor/ReviewTime.kt` (pure Kotlin, no Android imports):

  ```kotlin
  object ReviewTime {
      /** Position shown to the user: never below 0, never above the total. */
      fun clampPosition(posMs: Long, totalMs: Long): Long = posMs.coerceIn(0L, totalMs.coerceAtLeast(0L))
      /** "m:ss", whole seconds truncated (body of MainActivity.fmt). */
      fun format(ms: Long, locale: Locale): String { val s = ms / 1000; return String.format(locale, "%d:%02d", s / 60, s % 60) }
  }
  ```

- `MainActivity.kt:2722-2737` (`updateReviewPosition`): after `:2728` add
  `val shown = ReviewTime.clampPosition(pos, total)`; use `shown` for `scrubBar.positionMs` (`:2732`) and the status
  text (`:2736`). Keep the raw `pos` for `syncReviewOverlayAudio` (`:2729`), `reviewBar.updatePlayback` (`:2730`) and
  `captionView.setTime` (`:2733`), so overlay audio and captions are not shifted.
- `MainActivity.kt:3270-3273`: `fmt(ms)` delegates to `ReviewTime.format(ms, Locale.getDefault())` – identical output
  for the other callers (`:3115`, `:3173`, `:3247`, `:3249`).
- Check that the scrub bar's drag end (`ScrubBarView.kt:44`, `:224`) still seeks correctly: it reports its own
  `scrubPos`, so clamping `positionMs` from outside changes no seek target.
- New test `app/src/test/java/de/codinix/videoeditor/ReviewTimeTest.kt` (JUnit 4.13.2, as the other tests).

**Rejected alternatives:**

- Round `fmt()` to the nearest second: 13 100 vs 12 400 still reads "0:13 / 0:12", and the recording timer and draft
  times (same function) would change.
- Replace `durationMs` with the real file duration (MediaMetadataRetriever or the player timeline): it is the actual
  root of the drift, but it changes stored drafts, the export timeline (`TimelineRemapTest`) and overlay/caption
  offsets. Too wide for a bug-fix release; recorded as a follow-up candidate, not part of 1.1.6.

**JVM unit tests (`ReviewTimeTest.kt`, run by `./gradlew testDebugUnitTest` in `build-test-lint`):**

- `clampPosition(13_100, 12_400) == 12_400` (the reported case)
- `clampPosition(-50, 12_400) == 0`, `clampPosition(5_000, 0) == 0`, `clampPosition(5_000, 12_400) == 5_000`,
  `clampPosition(12_400, 12_400) == 12_400`
- `format(0, Locale.US) == "0:00"`, `format(12_999, Locale.US) == "0:12"`, `format(60_000, Locale.US) == "1:00"`,
  `format(3_599_000, Locale.US) == "59:59"`
- composed: `format(clampPosition(13_100, 12_400), Locale.US) + " / " + format(12_400, Locale.US) == "0:12 / 0:12"`
- fa/ar digit shaping and bidi order of this string are A18, not part of 1.1.6.
