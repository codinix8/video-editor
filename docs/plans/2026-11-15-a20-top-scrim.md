## Behaviour with the A1 insets (PR-1)

PR-1 pads `binding.root` with `systemBars() or displayCutout()` **without** `enableEdgeToEdge()` (hub knowledge
#2663): on API 35/36 the black window background shows in a strip behind the status and navigation bar, on API 26–34
the insets are zero. The bugfix plan already states that "when the concept is approved, the listener moves from the
root to the top/bottom control groups". PR-6 does exactly that:

1. **Edge-to-edge on every API level.** In `MainActivity.onCreate`, before `setContentView(binding.root)` (`:276`):
   `enableEdgeToEdge(statusBarStyle = SystemBarStyle.dark(Color.TRANSPARENT))` from `androidx.activity`
   (`activity-ktx:1.9.3`, `app/build.gradle.kts:94`; `MainActivity` is an `AppCompatActivity`, `:60`, which is a
   `ComponentActivity`). `navigationBarStyle` stays the library default (keeps the system contrast scrim for 3-button
   navigation). `SystemBarStyle.dark` keeps the status-bar icons light – the concept's
   `isAppearanceLightStatusBars = false` – on every API level.
2. **Root keeps only left/right padding** (`bars.left`, `0`, `bars.right`, `0`). The app is portrait-only
   (`AndroidManifest.xml:33`), so these are 0 in practice; they stay as a guard for a side cutout.
3. **Top/bottom insets move to spacer views** (new, see layouts): `insetTop.height = bars.top`,
   `insetBottom.height = bars.bottom` in both layouts, `topScrim.height = bars.top + 120 dp`. The listener still
   returns `WindowInsetsCompat.CONSUMED`, so no child applies the insets a second time (PR-1's double-padding guard
   stays valid; no `fitsSystemWindows` anywhere).
4. `PreviewView` and `PlayerView` stay `match_parent` on the root: the video now runs under the status and navigation
   bar on every API level (concept: "Das Video bleibt Vollbild").
5. Sheets: unchanged. `BottomSheetDialog` windows are separate; PR-1's conditional `Sheet.kt` bottom padding (if it
   was needed) stays.

## Min API 26 approach

- `enableEdgeToEdge()` (activity 1.8+) works from API 21: it sets the decor to not fit system windows, transparent
  system bars, and `layoutInDisplayCutoutMode` (`SHORT_EDGES` on API 28–29, `ALWAYS` on 30+). On API 26/27 the
  cutout inset is simply 0.
- The gradient uses `GradientDrawable(Orientation.TOP_BOTTOM, IntArray)`: more than three colours, spaced evenly,
  available on all supported levels. `GradientDrawable.setColors(int[], float[])` (custom offsets) needs API 29 and
  is **not** used.
- No XML `<gradient>`: it only has start/center/end colours, which gives the visible edge the ui-cheatsheet warns
  about ("Gradient fade has a visible edge → eased gradient with extra colour stops"). That is why the scrim is built
  in code instead of a new drawable XML.
- No blur (`RenderEffect` needs API 31 and costs a layer over a live camera preview); a plain alpha gradient is cheap
  and identical on all levels.

## Scrim values

| Property | Value | Reason |
|----------|-------|--------|
| Height | `bars.top + 120 dp` (concept: 120 dp gradient) | covers clock + segment bar (12 + 6 dp), status pill and settings button (bottom edge ≈ 12 + 6 + 14 + 32 + 12 + 44 ≈ 120 dp below the inset) |
| Colour | black only, alpha varies | no tint over the user's footage |
| Top alpha | `0x8C` (55 %) | white text on pure white footage under 55 % black = `#737373` → contrast 4.7 : 1 (WCAG AA for text). 40 % would give `#999999` → 2.8 : 1 (fails). Same value as the A22 outline. |
| Stops (alpha share of `0x8C`, evenly spaced) | 1.00, 0.86, 0.62, 0.36, 0.14, 0.00 | eased fade-out, no visible lower edge |
| Segment bar position (≈ 0.25 of the height with a 24 dp status bar) | ≈ 45 % black | white segment on white footage → `#8C8C8C`, ≥ 3 : 1 for a non-text UI element; the A22 outline adds the edge |
| Animation | none (static) | the scrim is part of the layout; nothing appears or moves, so no reduced-motion path is needed |

New file `app/src/main/java/de/codinix/videoeditor/ScrimGradient.kt` (pure Kotlin, no Android import in the
function under test):

- `const val SCRIM_HEIGHT_DP = 120`, `const val SCRIM_MAX_ALPHA = 0x8C`,
  `val SCRIM_STOPS = floatArrayOf(1f, 0.86f, 0.62f, 0.36f, 0.14f, 0f)`.
- `fun scrimColors(maxAlpha: Int = SCRIM_MAX_ALPHA, stops: FloatArray = SCRIM_STOPS): IntArray` → ARGB ints
  `(round(maxAlpha * s) shl 24)` (RGB 0).
- `fun topScrimDrawable() = GradientDrawable(GradientDrawable.Orientation.TOP_BOTTOM, scrimColors())` (Android part,
  not unit-tested).

## Design rules applied (for Design-Abnahme)

- ui-cheatsheet: "Gradient fade has a visible edge → eased gradient with extra colour stops" → 6 eased stops in code
  instead of a 3-stop XML gradient.
- apple-design §12 "Scroll edge effects, not hard dividers … only where floating UI actually overlaps content" →
  scrim only at the top, where clock and controls float over the video; no opaque bar, no bottom scrim.
- apple-design §12 "Build nav/toolbars … as translucent layers with content underneath – not opaque bars that consume
  a fixed strip" → replaces PR-1's black strip with full-bleed video under a translucent scrim.
- apple-design §12 "Vibrancy keeps text legible over changing backgrounds" → contrast is computed for the worst
  case (pure white footage), not for typical footage.
- Restraint / no motion: the scrim is static; no new animation, so no reduced-motion variant is needed.

## Risks

- **Changes the look on every API level** (video under the status bar from API 26): intended by the approved concept;
  covered by the API 26/30/34 rows above.
- **Recording preview:** the top ≈ 15 % of the camera image looks darker than it will be recorded. Accepted by the

- **Double or missing padding** if a later PR adds `fitsSystemWindows` or a second listener: the single consuming
